# Security notes

What this implementation defends against, how, and where the limits are. Written so a reviewer
can check the claims against the code rather than take them on trust.

---

## Password storage

**Argon2id**, `memoryCost = 19456 KiB, timeCost = 2, parallelism = 1`, 32-byte output —
the minimum configuration in the OWASP Password Storage Cheat Sheet. Implemented in
[`server/src/lib/password.ts`](server/src/lib/password.ts) via `@node-rs/argon2`.

- Argon2id is memory-hard, so a GPU or ASIC attacker gains far less over a defender than they do
  against a fast hash such as SHA-256 or a low-cost bcrypt.
- Every password gets its own salt, generated by the library and stored inside the encoded
  `$argon2id$v=19$m=19456,t=2,p=1$…` string. Two accounts with the same password have different
  digests, so one cracked password does not reveal the others.
- The plaintext is never written to the database, never logged, and never appears in a response.
  `server/tests/security.test.ts` asserts this by reading the row directly and searching every
  column and the serialised row for the plaintext.

**Password policy.** At least 12 characters; at least three of {lowercase, uppercase, digits,
symbols}; must not contain the account's name or email local-part; rejected if it appears in a
bundled list of commonly breached passwords, or contains a keyboard or counting run. The client
mirrors these rules for instant feedback, but the server re-runs them on every register and
password change and is the only authority.

## Tokens

Two tokens with deliberately different jobs.

### Access token — short-lived, stateless, in memory

JWT **HS256**, **15 minutes**. Claims: `sub`, `sid`, `email`, `role`, `typ`, `iss`, `aud`, `jti`,
`iat`, `exp`.

Verification passes an explicit **algorithm allowlist** of `["HS256"]` plus the expected `iss` and
`aud`, then asserts `typ === "access"`. That allowlist is what blocks the classic `alg: none`
forgery and the RS256→HS256 confusion attack, where an attacker re-signs a token using the
public key as an HMAC secret.

In the browser the access token lives in a **module-level variable**
([`web/src/lib/api.ts`](web/src/lib/api.ts)) — never `localStorage` or `sessionStorage`. Anything
script can read is something injected script can exfiltrate. A variable dies with the tab, and
durable sessions come from the cookie below instead.

### Refresh token — long-lived, stateful, invisible to script

A **256-bit opaque random value**. What is persisted is only its **SHA-256 digest**, so a
database leak does not hand an attacker usable tokens. Delivered as
`HttpOnly; SameSite=Strict; Secure` (in production), scoped to `/api/v1/auth`.

`HttpOnly` means an XSS payload cannot read it. `SameSite=Strict` means the browser will not
attach it to a request originating from another site. The path scope means it is not sent to any
endpoint that does not need it.

## Rotation and reuse detection

The strongest property here, implemented in
[`server/src/services/sessionService.ts`](server/src/services/sessionService.ts) and the refresh
route.

Every refresh mints a successor token in the same **family** and marks its predecessor
`revoked_reason = 'rotated'` with `replaced_by` pointing at the successor, inside one
transaction.

A refresh token is therefore valid exactly once. If a **retired** token is presented, there are
only two explanations: a client replayed an old value, or someone copied it. Both are treated as
theft:

1. Every session sharing the `family_id` is revoked with reason `reuse_detected`.
2. A `token_reuse_detected` audit event is written.
3. The cookie is cleared and the response is `401 SESSION_REVOKED`.

The attacker is cut off, and the legitimate user is logged out and can see why in their activity
log. Without this, a stolen refresh token grants indefinite access and nothing ever notices.

The client cooperates: concurrent `401 TOKEN_EXPIRED` responses share a **single in-flight
refresh promise**, so a page that fires six requests on mount presents the rotating token once.
Without that, five of the six would look exactly like reuse — and the server would be right to
burn the family.

## Revocation that actually revokes

A stateless JWT normally cannot be withdrawn before it expires, which makes "sign out everywhere"
a lie for up to the token lifetime.

Here `authenticate` ([`server/src/middleware/authenticate.ts`](server/src/middleware/authenticate.ts))
performs four checks on every authenticated request:

1. The JWT verifies against the allowlisted algorithm, issuer and audience.
2. The user still exists.
3. The session named by the `sid` claim is still active — not revoked, not expired.
4. `iat >= floor(password_changed_at / 1000)` — a token minted before a password change is dead.

Checks 3 and 4 are what make revocation real. `POST /auth/logout-all` invalidates live access
tokens immediately, and changing a password signs out every other device. The cost is one indexed
SQLite read per request, which is the right trade at this scale.

## Account enumeration and timing

`POST /auth/login` returns a byte-identical `401 INVALID_CREDENTIALS` body for a wrong password
and for an email that has no account. `scripts/smoke.mjs` and the test suite both assert the two
responses are identical once `requestId` is stripped.

Identical bodies alone are not enough: if an unknown email returned immediately while a known one
paid the Argon2id cost, the timing difference would leak membership. So an unknown email is still
verified against a precomputed **dummy hash** with the same parameters before the request fails.

Registration is the unavoidable exception — `409 EMAIL_TAKEN` necessarily confirms an address is
in use. This is the standard trade for a usable sign-up form, and the rate limiter bounds how fast
a list can be tested.

## Brute force

- **Account lockout.** Five failed logins set `locked_until = now + 15 minutes`. While locked,
  login returns `423 ACCOUNT_LOCKED` with `details.retryAfterSeconds`. A successful login clears
  the counter. An `account_locked` audit event is written.
- **Rate limits** (`express-rate-limit`): 10 per 15 minutes per IP+email on login and register,
  60 per 15 minutes on refresh, 300 per 15 minutes per IP across `/api`. IPv6 addresses are
  bucketed with the library's `ipKeyGenerator`, so an attacker cannot trivially rotate through a
  /64 they control.

Lockout is per account and rate limiting is per IP, so neither alone is sufficient and together
they cover both a single account under attack and a single source attacking many accounts.

## CSRF

Refresh and logout authenticate with a cookie, which the browser attaches automatically to
cross-site requests — the precondition for CSRF. Mitigated in two independent layers:

1. `SameSite=Strict` on both cookies.
2. **Double-submit token.** `GET /auth/csrf` sets a readable `csrf_token` cookie; every mutating
   request must echo it in `X-CSRF-Token`. Compared with a constant-time check. A cross-site page
   can cause the cookie to be *sent* but cannot *read* it, so it cannot construct the header.

Missing either half is a failure, never a skip — an attacker cannot bypass the check by omitting
the header.

## Authorization and tenant isolation

Vault queries are always scoped by `user_id` in the SQL itself, not filtered after the fact.
Requesting another account's item returns **`404 NOT_FOUND`**, byte-identical to an id that never
existed. Returning `403` would confirm the id is real, turning the endpoint into an oracle for
enumerating other people's records.

## Transport and application hardening

- `helmet` with a Content-Security-Policy; framing blocked via `frame-ancestors 'none'`.
- CORS restricted to the configured `WEB_ORIGIN` with credentials enabled.
- `x-powered-by` disabled; `trust proxy` set so client IPs are correct behind a reverse proxy.
- JSON bodies capped at 32 kB (`413 PAYLOAD_TOO_LARGE`).
- All input validated with zod before it reaches a handler; parsed values replace the raw body,
  so unknown fields are stripped rather than passed through.
- SQL runs exclusively through **prepared statements** with bound parameters.
- In production, unexpected errors return `"Something went wrong."` with no stack or internal
  message. The real error is logged server-side against the request id.

## Secrets

`JWT_SECRET` must be at least 32 characters. **In production the server refuses to boot without
one.** In development it generates an ephemeral secret at startup and logs a warning; tokens then
stop working across restarts, which is intended — it makes the missing configuration obvious
rather than silently shipping a default key.

`.env` is gitignored. `server/.env.example` is committed with the key blank and the command to
generate one. The only credential in this repository is the seeded demo password, which exists in
`server/src/db/seed.ts` and is published deliberately so the demo is reproducible.

## Audit log

`auth_events` is append-only and records register, login (success and failure), logout,
logout-all, refresh, **reuse detection**, password change, profile update, session revocation,
lockout and rate limiting — each with outcome, IP and user agent. Users see their own log at
`/sessions`. Writing an audit row can never fail a request: the insert is wrapped so a logging
problem does not become an availability problem.

## Known limits

Stated plainly, because an incomplete threat model is itself a risk.

| Limit | Consequence |
|---|---|
| No email verification | Anyone can register an address they do not control. |
| No password reset | A forgotten password cannot be recovered. |
| No multi-factor authentication | A stolen password is sufficient to sign in. The session model would accommodate MFA, but it is not implemented. |
| Breached-password list is a bundled sample | Not the full Have I Been Pwned corpus; a k-anonymity range query would be the production answer. |
| Lockout is a denial-of-service lever | Someone who knows an email can lock it for 15 minutes at a time. The usual mitigations are a CAPTCHA or risk-based throttling. |
| SQLite, single node | Correct for a reference implementation. Sessions and audit rows would need a real database to scale horizontally. |
| Rate limiting is in-process | Counters are per instance and reset on restart. A shared store is needed behind multiple instances. |
| HTTPS terminates upstream | The app serves plain HTTP; `Secure` cookies assume a TLS-terminating proxy in front. |
| Audit log stores IP and user agent | Personal data under GDPR-style regimes. A real deployment needs a retention policy. |
